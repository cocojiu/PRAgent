文档格式说明：根据“除 README.md 外不得提交 Markdown 文档、测试脚本不得提交 Git”的仓库约束，本报告使用 TXT，且本次不执行 Git 暂存或提交。

一、结论摘要

项目已经具备较好的生产化基础，不属于需要推倒重构的状态。认证链路采用内存访问令牌、HttpOnly 刷新 Cookie、CSRF 校验和刷新令牌轮换；外部请求有主机/端口策略；Docker 镜像使用非 root 用户；RabbitMQ 发布确认、补偿、任务抢占、数据库归档、指标基数限制、API 契约快照和 MySQL/RabbitMQ 集成 CI 均已落地。

当前最应优先处理的不是代码风格，而是以下四类问题：

1. 通知手动重试在数据库事务提交前直接发布 RabbitMQ，且没有状态白名单和并发抢占，存在重复通知及“消息已发、事务回滚”的一致性风险。
2. 前端部分异步流程缺少请求序号或取消机制，慢响应可能覆盖新路由、新搜索条件；集成配置的四接口并发保存可能形成部分成功。
3. 大表迁移、逐行插入和首屏公共依赖仍有明确的扩容与性能成本。
4. 构建版本、覆盖率门禁、真实浏览器验收和依赖治理尚未形成完全可复现的闭环。

建议先完成 P0 和 P1，确认行为正确后再进行架构收敛。不要为了减少文件数而先做大规模重构。

四、P0 优化项

P0-1 通知手动重试需要改为“受控状态迁移 + 提交后发布”

证据：

- repoguard-backend/src/main/java/com/repoguard/agent/service/impl/NotificationEventQueryServiceImpl.java:68
- repoguard-backend/src/main/java/com/repoguard/agent/service/impl/NotificationEventQueryServiceImpl.java:76
- repoguard-backend/src/main/java/com/repoguard/agent/service/impl/NotificationEventQueryServiceImpl.java:77
- repoguard-backend/src/main/java/com/repoguard/agent/notification/NotificationDispatchServiceImpl.java:50
- repoguard-backend/src/main/java/com/repoguard/agent/notification/NotificationDispatchServiceImpl.java:60
- repoguard-backend/src/main/java/com/repoguard/agent/notification/NotificationEventPublishCoordinator.java:35

现状：retryEvent() 带 @Transactional，先无条件把事件改为 PENDING，再调用 publishExistingEvent()；后者直接执行 publish()，没有使用项目已经存在的 publishAfterCommit()。更新条件也没有限制原状态或声明抢占者。

风险：

- 两个并发重试请求都可能发布同一个事件。
- 已经 DELIVERED/PUBLISHED 的事件也能被 API 再次改为 PENDING 并发布。
- RabbitMQ 已确认后，如果后续 select/组装响应抛异常，数据库事务回滚，但消息无法回滚，补偿任务可能再次发布。
- 当前单测只验证“重置并调用发布”，没有覆盖并发、事务回滚和已完成状态。

建议：

1. 增加单条条件更新：仅允许 PUBLISH_FAILED/DELIVERY_FAILED 等可重试状态转为 PENDING，并通过版本号或 publish_claimed_at/publish_claimed_by 完成 CAS 抢占。
2. 事务内只保存重试意图；提交后调用 publishAfterCommit()，或完全交给现有补偿 worker 扫描 PENDING 事件。
3. API 返回 queued/accepted 语义，不要把 RabbitMQ 发布成功与最终通知送达混为一体。
4. 消费端继续以 eventKey/eventId 做幂等，防止消息系统的至少一次投递转化为重复外部通知。

验收标准：

- 同一事件 20 个并发重试请求最多一个获得发布权。
- DELIVERED/PUBLISHED 事件返回 409 或业务拒绝，不改变状态。
- 强制事务回滚时 RabbitMQ 不出现消息。
- after-commit 发布失败时事件保留为可补偿状态，并能被 recovery worker 恢复。

五、P1 优化项

P1-1 集成配置“保存全部”存在部分成功

证据：

- repoguard-frontend/src/features/integrations/composables/useIntegrationConfigPersistence.ts:88
- repoguard-frontend/src/features/integrations/composables/useIntegrationConfigPersistence.ts:94
- repoguard-frontend/src/features/integrations/composables/useIntegrationConfigPersistence.ts:102

现状：GitHub、MySQL、RabbitMQ、Review Policy 四个独立 PUT 通过 Promise.all 并发执行。任意一个失败时，其余请求不会取消，已经成功的配置仍然持久化，但页面只显示整体失败且不应用成功响应。

建议二选一：

- 交互改为每张集成卡独立保存、独立反馈，这是改动最小且语义最清楚的方案。
- 如果业务必须“全部保存”，增加后端批量命令，在同一数据库事务内校验并更新全部配置；外部连接测试与持久化分离。

同时把 loadConfig() 的 Promise.all 改为 Promise.allSettled，允许成功配置先展示，并在具体卡片标记失败。保存失败后主动重新拉取服务端状态，避免页面与数据库不一致。

验收标准：构造四个请求中任一失败，用户能明确看到每项结果；页面最终状态与数据库一致，不出现静默部分保存。

P1-2 任务详情主请求可能被旧路由响应覆盖

证据：

- repoguard-frontend/src/features/review-detail/composables/useReviewDetailLoader.ts:54
- repoguard-frontend/src/features/review-detail/composables/useReviewDetailLoader.ts:75
- repoguard-frontend/src/features/review-detail/composables/useReviewDetailLoader.ts:76
- repoguard-frontend/src/pages/ReviewDetailPage.vue:716

现状：loadDetail() 在请求前读取 id，但响应回来后没有确认当前路由 id 仍然相同，也没有 requestSeq/AbortController。快速从任务 A 导航到任务 B 时，A 的慢响应可能最后写入 selectedTask；旧请求的 finally 也可能提前关闭新请求的 loading 状态。

建议：复用 useReviewTasksList 已有的 requestSeq 模式，或在 API 层支持 AbortSignal。只有“请求序号仍是最新且 id 等于当前路由”时才允许写状态、错误和 loading。pollReviewStatus() 同样应用该规则。

验收标准：人为让 A 延迟、B 快速返回，最终 URL、详情、轮询对象和 loading 必须全部属于 B。

P1-3 用户搜索存在请求风暴和乱序覆盖

证据：

- repoguard-frontend/src/pages/UserManagementPage.vue:262
- repoguard-frontend/src/pages/UserManagementPage.vue:270
- repoguard-frontend/src/pages/UserManagementPage.vue:454

现状：keyword 每次输入都会立即调用服务端查询，没有 debounce，也没有请求序号。快速输入可能产生多次数据库 LIKE 查询，旧关键字的慢响应还能覆盖新关键字结果。分页和过滤刷新期间 loading 也没有统一覆盖。

建议：增加 300~400ms debounce、requestSeq/AbortController，并把所有列表入口收敛为一个 loadUsers({ reason })。后端对 username/email 模糊查询结合真实数据量核对索引和执行计划；数据量较大时考虑前缀搜索或专用检索字段。

验收标准：连续输入 10 个字符只触发 1~2 次请求；乱序响应不改变最终列表；切页和筛选时有一致的加载状态。

P1-5 审查结果和变更文件使用逐行 INSERT

证据：

- repoguard-backend/src/main/java/com/repoguard/agent/worker/ReviewFindingReplacementService.java:29
- repoguard-backend/src/main/java/com/repoguard/agent/worker/ReviewFindingReplacementService.java:32
- repoguard-backend/src/main/java/com/repoguard/agent/worker/ChangedFileReplacementService.java:21
- repoguard-backend/src/main/java/com/repoguard/agent/worker/ChangedFileReplacementService.java:23

现状：删除旧记录后，在事务内对每个 finding/file 单独调用 mapper.insert()。大 PR 会产生 N 次数据库往返，并延长持锁时间；事务并发冲突时整个批次还可能重试。

建议：增加显式 batchInsert SQL（foreach values）或受控的 MyBatis batch executor，按 100~500 条分批；依据字段大小和 max_allowed_packet 调整批次。保留去重和整体事务语义，并记录 batch size、SQL 时长和失败批次。

验收标准：500 文件、1,000 findings 的持久化 SQL 次数从约 1,500 次降到个位数或低两位数；结果数量和事务回滚语义不变。

P1-7 应用限流只在单 JVM 内有效

证据：

- repoguard-backend/src/main/java/com/repoguard/agent/security/AuthAttemptLimiter.java:20
- repoguard-backend/src/main/java/com/repoguard/agent/security/AuthAttemptLimiter.java:47
- repoguard-backend/src/main/java/com/repoguard/agent/github/webhook/GithubWebhookRateLimiter.java:20
- repoguard-backend/src/main/java/com/repoguard/agent/github/webhook/GithubWebhookRateLimiter.java:50

现状：认证和 webhook 限流均使用进程内 ConcurrentHashMap，并对整张 map 加 synchronized。多实例时限额按实例数放大；单实例高并发时所有 key 竞争同一把锁。当前 Nginx 还有边缘限流，可以降低风险，但应用层语义仍依赖单实例拓扑。

验收标准：两实例压测下总限额不随实例数翻倍；2 万离散 key 压测不出现明显全局锁排队或无界内存增长。

证据：

P1-A 通知投递需要原子领取和完成栅栏

证据：

- repoguard-backend/src/main/java/com/repoguard/agent/notification/NotificationDeliveryWorker.java:100-110
- repoguard-backend/src/main/java/com/repoguard/agent/notification/NotificationDeliverableEventQuery.java:17-27

- repoguard-backend/src/main/resources/db/migration/V26__create_notification_delivery_logs.sql:42-59

现状：消费者先读取事件，再把状态改为 DELIVERING，随后调用外部渠道。状态更新只排除 DELIVERED，没有限定必须从 PUBLISHED/DELIVERY_FAILED 等状态迁移，也没有检查数据库影响行数。DELIVERING 仍会被查询层视为可投递。投递日志在“检查成功记录”和“发送”之间也存在时间窗口，数据库没有可承担并发幂等语义的唯一约束。

风险：RabbitMQ 的至少一次投递、消费者并发或消息重复均可能让两个执行者同时发送同一通知。即使事后只有一条成功日志，外部 webhook、邮件等副作用已经发生。

建议：

1. 使用条件更新原子领取：仅允许 PUBLISHED/DELIVERY_FAILED -> DELIVERING，并要求影响行数等于 1。
2. 增加 claimed_at、claimed_by 和领取租约，支持宕机后的超时回收。
3. 完成/失败更新携带领取令牌，拒绝过期执行者覆盖新执行者的结果。
4. 明确渠道幂等键和投递日志唯一语义；不能做到严格 exactly-once 的渠道，至少要阻止应用内部并发重复发送。
5. 增加重复消息、双消费者、执行者超时恢复的真实并发集成测试。

证据：

- repoguard-backend/src/main/java/com/repoguard/agent/service/impl/DataRetentionServiceImpl.java:108-129

现状：cleanup() 的外层事务尚未由 Spring 代理提交时，成功审计已经通过 REQUIRES_NEW 独立提交；finally 中的租约释放也在外层事务真正完成前提交。

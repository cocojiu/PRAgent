### 2026-06-20 架构师复盘与后续优化建议

本轮基于当前仓库结构、后端核心链路、前端 feature 拆分、RabbitMQ/通知/LLM 相关实现进行架构复盘。当前系统已经从早期演示形态演进为以 `ReviewTask` 为主线的 PR 审查工作流平台，具备任务创建、异步执行、GitHub diff 拉取、规则/LLM 审查、评论预览与回写、通知 outbox、后台运维和基础观测能力。后续优化不建议继续做低收益的行数型拆分，应优先围绕线上韧性、审查质量闭环和配置治理推进。

#### 优先级建议

| 优先级 | 优化方向 | 目标 | 建议落点 |
| --- | --- | --- | --- |
| P1 | 审查执行链路继续领域化 | 降低 `ReviewTaskExecutorImpl` 编排复杂度，为并发 worker、重试恢复和策略扩展留出边界 | 任务抢占/状态应用、changed files 持久化、finding 持久化、完成/失败状态应用 |
| P1 | 消费侧幂等与卡死恢复 | 避免 `REVIEWING` 长时间悬挂、重复消费、重复回写 GitHub 评论 | `ReviewTaskWorker`、`ReviewTaskExecutorImpl`、评论发布批次表、定时补偿任务 |
| P1 | LLM 审查质量治理闭环 | 让系统从“可审查”走向“可持续变准” | prompt version、解析失败摘要、finding 反馈统计、模型/仓库/规则维度质量指标 |
| P1 | 配置生命周期治理 | 区分编辑配置、生效配置和任务运行时快照，降低运行中配置变化带来的不确定性 | `IntegrationConfig`、`ReviewPolicyConfig`、`ReviewRuleConfig`、`SystemSettingsConfig` |
| P2 | 通知投递可观测闭环 | 让通知失败可分类、可重试、可人工干预、可统计 | `NotificationEvent`、`NotificationDeliveryLog`、通知运维页 |
| P2 | API 契约治理 | 降低前后端 DTO 字段漂移风险 | OpenAPI/契约测试、前端 `src/types` 生成或半自动校验 |
| P2 | 查询与索引持续校准 | 支撑任务列表、dashboard、通知历史、评论历史数据增长 | Flyway 索引迁移、慢查询复盘、分页游标或组合索引优化 |
| P3 | 多租户/多仓库权限模型 | 支撑团队级使用和仓库级授权 | 用户-组织-仓库-角色模型、仓库可见性过滤 |
| P3 | 审查策略插件化 | 支撑 Secret 扫描、依赖风险、测试覆盖率等 reviewer pipeline 扩展 | `PullRequestReviewer` 组合管线、规则/LLM/安全扫描插件 |

#### 近期最值得先做的三项

1. 审查执行链路继续拆出高价值边界。当前 `ReviewTaskExecutorImpl` 仍承担任务抢占、diff 持久化、审查调用、finding 替换、状态流转、timeline、通知和指标编排。A145/A146 已经拆出 finding 去重和 timeline 追加，下一步优先抽取 changed files 替换落库、完成/失败状态应用等可独立测试边界，不建议一次性重写 worker。
2. 补强 `REVIEWING` 卡死恢复。需要定义超时阈值、恢复策略和运维入口，例如将长时间 `REVIEWING` 的任务标记为 `FAILED` 或重新入队，并记录 timeline 与失败原因。该能力应与现有 MQ 发布补偿、任务重试入口保持一致。
3. 建立 LLM 质量反馈闭环。已有 token、cost、fallback、parse status、finding feedback 等基础字段，建议增加 prompt version、模型响应摘要/解析失败摘要、误报/采纳统计，并在 dashboard 或独立质量页按仓库、模型、规则、时间窗口聚合。

#### 验收口径

- 审查执行链路新增边界必须有独立单元测试，且保持 `ReviewTaskExecutorImplTest`、`ReviewTaskStateMachineTest` 通过。
- 卡死恢复必须覆盖重复执行、并发 claim、超时任务、正常 `REVIEWING` 任务不误伤等用例。
- LLM 质量治理不记录真实密钥，不在日志和 API 响应泄露原始敏感内容；如保留原始响应，也必须脱敏、限长并可配置关闭。
- 配置生命周期调整不得影响正在执行任务的确定性；任务详情应能追溯当次审查实际使用的策略摘要。
- 通知投递优化必须保留 outbox 事务语义，失败重试、人工重投和最终状态应可在通知运维页解释清楚。

阶段结论：
- 当前项目最有价值的优化方向已经从“补基础能力”转为“提升线上韧性和平台化边界”。后续每轮优化应优先选择能独立验证、能降低故障恢复成本、能提升审查质量的数据闭环，不再为了降低单文件行数而拆分。

| P3 | API 契约自动化 | 降低前后端 DTO 手写同步成本，减少字段漂移 | OpenAPI、契约测试、前端类型生成或校验 |

#### 建议优先进入路线图的四项

1. 状态机正式化。将 `QUEUED`、`REVIEWING`、`COMPLETED`、`FAILED`、`PUBLISH_FAILED` 以及人工审核、评论回写相关状态整理为迁移表，并补充非法迁移测试。后续卡死恢复、重试补偿和人工重投都应先通过状态机约束。
2. 策略快照。每个审查任务需要能够解释“当时使用了什么规则、什么模型、什么 prompt 版本、什么 fallback 策略”。这项能力会直接支撑审查争议排查、历史结果复盘和模型质量评估。
3. 质量评测集。选取典型 PR case，覆盖安全问题、空结果、误报、复杂 diff、大文件、测试缺失、解析失败等场景。每次修改 LLM prompt、规则、chunk 或解析器后，都应能执行一次小型回归评测。
4. 仓库级权限模型。当前 admin/user 粗粒度角色适合内部早期使用，但团队级场景需要区分用户可见仓库、可触发审查、可回写评论、可改规则和可查看审计日志的权限边界。

#### SLO 建议指标

- 任务创建成功率。
- 审查任务平均完成时间和 P95 完成时间。
- `REVIEWING` 超时任务数量。
- GitHub diff 拉取失败率。
- LLM fallback 率、解析失败率和平均成本。
- GitHub 评论回写成功率、跳过率和失败率。
- 通知事件发布成功率和投递成功率。
- 配置连接测试成功率。

#### 验收口径

- 状态机文档必须与 `ReviewTaskStateMachine` 单元测试保持一致，新增状态或迁移时同步更新。
- 策略快照不能保存真实密钥；任务详情只展示脱敏后的策略摘要、版本和开关信息。
- 评论回写幂等必须有数据库唯一约束或等价强约束，不能只依赖前端按钮状态。
- 质量评测集应能在无真实 GitHub 写权限的情况下运行，避免对外部生产资源产生副作用。
- 仓库级权限必须同时约束后端查询和写接口；前端隐藏按钮只能作为体验优化，不能作为权限边界。

阶段结论：
- 补充路线图的重点不是继续扩大功能，而是让 RepoGuard Agent 具备“状态可解释、策略可追溯、质量可度量、权限可治理、运行可观测”的平台化基础。建议后续优先围绕这四类能力安排里程碑。

### 2026-06-20 审查能力专项优化建议

本节聚焦 RepoGuard Agent 的核心产品能力：代码审查质量。当前系统已经具备规则审查、LLM 审查、fallback、diff chunk、finding 去重合并、finding feedback 和 LLM 成本/状态记录等基础能力。后续审查能力优化不应只追求“模型更强”，而应围绕上下文、规则、评测、反馈和可解释性形成稳定方法论。

#### 审查能力优化矩阵

| 优先级 | 优化方向 | 目标 | 建议落点 |
| --- | --- | --- | --- |
| P1 | 审查上下文增强 | 降低只看 diff 带来的误报和漏报，提升 LLM 对真实影响面的判断能力 | `GithubPullRequestClientImpl`、`GithubPullRequestDiff`、`PullRequestDiffChunker`、`LlmPullRequestReviewer` |
| P1 | 审查能力矩阵 | 明确 RepoGuard 审什么、怎么分级、什么情况阻断合并，避免泛化 prompt 导致输出不稳定 | 规则配置、prompt 模板、finding category/severity 定义 |
| P1 | 项目专属规则库 | 先覆盖本项目高价值风险点，让规则审查成为稳定底座，LLM 负责精审和解释 | `RuleBasedPullRequestReviewer`、`ReviewRuleConfig`、规则命中统计 |
| P1 | 规则先筛 + LLM 精审 | 降低 token 成本，避免大 diff 稀释 LLM 注意力，让高风险片段获得更多上下文预算 | diff 预处理、风险片段选择器、chunk 策略 |
| P1 | 审查质量评测集 | 为 prompt、规则、chunk、解析器调整提供回归基准，量化误报、漏报和可采纳率 | 测试资源、离线评测命令、典型 PR case |
| P2 | finding 可解释性增强 | 让用户理解为什么报、影响是什么、如何修，提升结果可采纳率 | `ReviewFindingResult`、`ReviewFinding`、详情页展示 |
| P2 | 置信度与阻断策略 | 区分高置信风险、低置信建议和可阻断问题，支撑后续合并门禁 | `confidence`、`isBlocking`、规则/LLM 合并策略 |
| P2 | 反馈反哺审查 | 将用户对 finding 的确认、误报、忽略沉淀为规则和 prompt 优化依据 | `FindingFeedbackServiceImpl`、Dashboard 质量统计 |
| P2 | 多维审查画像 | 按安全、稳定性、性能、测试、兼容性、架构维护性输出结构化结果 | finding category、风险画像、Dashboard 质量视图 |

#### 建议优先覆盖的审查维度

1. 安全：密钥泄露、SQL 注入、SSRF、权限绕过、路径穿越、敏感日志、危险反序列化。
2. 稳定性：空指针、异常吞噬、重试风暴、并发竞态、状态机非法迁移、长事务和连接占用。
3. 可维护性：职责混杂、重复逻辑、复杂方法、异常处理不一致、DTO/实体边界混乱。
4. 性能：N+1 查询、缺索引、无界分页、大对象响应、同步外部调用阻塞核心事务。
5. 测试：核心分支缺测试、失败路径缺测试、边界输入缺测试、只改实现未补契约测试。
6. 兼容性：API 字段破坏性变更、数据库迁移风险、配置默认值风险、前后端类型漂移。
7. 项目治理：权限注解缺失、敏感配置未脱敏、MQ 发布失败无补偿、评论回写无幂等、任务状态未经过状态机。

#### 项目专属规则库首批建议

- Controller 写接口必须有认证和角色控制，配置写入、评论回写、用户管理等高危操作必须限制管理员或更高权限。
- API 响应、日志、异常和测试断言不得输出 GitHub Token、LLM API Key、Webhook secret、数据库密码等真实密钥。
- 任务状态变更必须通过明确状态机或状态应用边界，不允许在业务代码中随意写入状态字符串。
- RabbitMQ 发布失败必须进入可补偿状态，并具备重试次数、下次重试时间和失败原因。
- GitHub 评论回写必须具备批次级或 finding 级幂等保护，避免重复发布。
- 新增外部调用必须经过错误分类、超时、重试/限流/熔断策略和指标记录。
- 新增配置必须具备校验、脱敏返回、连接测试或运行时可解释的失败原因。
- 新增数据库迁移必须评估索引、默认值、回滚影响和历史数据兼容性。

#### 审查结果字段增强建议

| 字段 | 含义 | 用途 |
| --- | --- | --- |
| `category` | 安全、稳定性、性能、测试、兼容性、维护性等分类 | 支撑前端筛选、质量统计和规则矩阵 |
| `confidence` | HIGH/MEDIUM/LOW | 区分高置信缺陷和低置信建议 |

#### 审查质量评测集建议

首批评测集建议覆盖以下 PR case：

1. 存在真实安全问题的 PR，例如密钥泄露、权限缺失、敏感日志。
2. 存在稳定性问题的 PR，例如状态机非法迁移、异常吞噬、外部调用缺少超时。
3. 大 diff PR，用于验证 chunk 策略、成本和结果合并稳定性。
4. 只有文档、样式或无风险重命名的 PR，用于评估误报率。
5. 涉及数据库迁移的 PR，用于检查索引、默认值和兼容性风险。
6. 涉及 RabbitMQ、通知、GitHub 回写的 PR，用于检查补偿、幂等和可观测性。
7. 应该无 finding 的干净 PR，用于校准低风险输出和噪声控制。

#### 近期最值得先做的三项

1. 建立审查能力矩阵。先明确 RepoGuard 当前要审的风险类别、每类风险的 severity 和是否阻断合并，不再只依赖通用 LLM 提示词。
2. 增加项目专属规则库。优先覆盖权限、密钥、状态机、MQ 补偿、评论幂等、外部调用治理和配置脱敏，这些规则与当前项目架构强相关，收益稳定。
3. 建立小型评测集。先不追求规模，选 10-20 个代表性 PR case，能在本地或 CI 中离线运行，用来观察误报率、漏报率、可采纳率和 token 成本变化。

#### 验收口径

- 新增审查维度必须能映射到稳定 `category` 和 `severity`，不能只停留在 prompt 文案。
- 项目专属规则必须有单元测试或评测 case，避免规则误伤大量正常变更。
- 质量评测集应能重复运行，且不依赖真实 GitHub 写权限或外部生产资源。
- finding 字段增强必须兼容历史数据和前端展示，不应破坏现有任务详情 API。
- LLM 输出增强必须同步更新解析器容错测试，保证模型漏字段、字段类型异常或输出非严格 JSON 时仍可降级处理。

阶段结论：
- 审查能力的下一阶段重点是“上下文增强 + 能力矩阵 + 项目专属规则 + 评测集 + 反馈闭环”。LLM 是推理引擎，规则、上下文、评测和反馈才是 RepoGuard Agent 长期审查质量的稳定底座。

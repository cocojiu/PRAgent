# RepoGuard Agent 企业级线上项目优化方案

文档版本：v1.0  
编制日期：2026-06-10  
适用项目：RepoGuard Agent  
审查范围：`repoguard-backend`、`repoguard-frontend`、`docs/release`、Flyway migration、构建与运行配置  
审查角色：资深架构师 / 企业级线上交付评审

## 1. 结论摘要

RepoGuard Agent 已具备企业内部 PR 智能审查平台一阶段上线的核心闭环：任务创建、RabbitMQ 异步执行、GitHub diff 拉取、LLM/规则审查、审查结果展示、失败重试、评论预览与回写、回写历史追踪、配置管理和基础验收文档。

从企业级线上项目标准看，当前代码更接近“可进入预发和灰度”的状态，距离“稳定生产长期运行”还需要补齐以下关键能力：

| 优先级 | 结论 | 上线影响 |
| --- | --- | --- |
| P0 | 认证授权、生产密钥强制校验、长事务拆分、MQ 失败治理必须先处理或由网关/运维方案强约束 | 未处理不建议直接开放生产访问 |
| P1 | GitHub/LLM 调用治理、任务幂等并发保护、配置一致性、可观测指标、数据库索引与归档需要进入近期迭代 | 影响稳定性、排障效率和容量 |
| P2 | 前端错误可读性、状态轻量轮询、历史分页、构建产物优化、接口版本化需要持续优化 | 影响体验和运维效率 |
| P3 | 文档模板、代码规范、规则市场、审查质量反馈闭环可作为后续增强 | 不阻塞一阶段上线 |

建议上线策略：

1. 生产发布前完成 P0 项，或给出等效外部控制措施和验收记录。
2. P1 项进入首个生产稳定性迭代，建议 1-2 个 Sprint 内完成。
3. P2/P3 纳入产品体验和平台化路线图。

## 3. 当前架构状态

### 3.1 已具备能力

| 领域 | 当前能力 |
| --- | --- |
| 应用分层 | Controller、Service、Worker、Review、GitHub、Mapper、DTO、Config、Common、Security 分层清晰 |
| 异步处理 | 使用 RabbitMQ 解耦任务创建与审查执行 |
| 数据管理 | 使用 MySQL 8 和 Flyway 管理任务、结果、配置、回写历史 |
| 外部集成 | 支持 GitHub REST API、OpenAI Chat Completions 兼容 LLM API |
| 敏感字段 | GitHub Token、LLM API Key、服务密码使用 AES-GCM 加密存储并脱敏返回 |
| 审查回写 | 支持行评论、PR 总评降级、幂等跳过、批次历史 |
| 前端体验 | 具备总览、任务、详情、规则、集成、系统设置页面 |
| 构建优化 | `vite.config.ts` 已按 `echarts`、`element-plus`、`vendor` 设置基础拆包 |

### 3.2 主要短板

| 短板 | 代码/配置依据 | 风险 |
| --- | --- | --- |
| 缺少应用内认证授权 | 未发现 Spring Security 或 RBAC 相关实现；所有 `/api/v1/**` Controller 直接暴露 | 配置、Token、评论回写等管理能力可能被未授权访问 |
| 生产密钥未强制禁止默认值 | `SecretCryptoService` 默认 `repoguard-local-dev-encryption-key` | 生产误用默认密钥会造成敏感配置可预测 |
| 外部 HTTP 调用在事务中执行 | `ReviewTaskExecutorImpl.execute` 标注 `@Transactional`，内部调用 GitHub 和 LLM | 长事务、连接占用、锁等待、超时回滚风险 |
| MQ 缺少失败治理 | 队列持久化存在，但未见 DLQ、重试退避、手动 ack、失败消息隔离 | Worker 异常时容易形成重复消费或不可观测失败 |
| 全局异常可能泄露内部信息 | `GlobalExceptionHandler.handleException` 直接返回 `exception.getMessage()` | 对外暴露内部路径、HTTP 细节、下游错误 |
| 配置测试与运行参数可能不一致 | 文档实测已发现 MySQL/RabbitMQ 配置页测试失败但运行服务正常 | 运维判断容易误判 |
| 数据归档未落地 | `retention_days` 有配置，但未见清理任务 | 数据增长后影响查询和存储成本 |
| 观测指标不足 | 仅暴露 `health,info`，未见 Micrometer 业务指标 | 难以量化 LLM、GitHub、MQ、回写失败率 |

## 4. 优先级定义

| 优先级 | 定义 | 处理要求 |
| --- | --- | --- |
| P0 | 生产阻断或高危安全/稳定性问题 | 上生产前修复或必须有等效控制和验收记录 |
| P1 | 核心链路稳定性、性能、可运维性问题 | 首个生产稳定性迭代完成 |
| P2 | 重要体验、效率和中长期可维护性问题 | 纳入近期产品迭代 |
| P3 | 增强项、规范项、平台化能力 | 进入路线图 |

## 5. P0 优化项

### P0-01 接入认证授权与最小权限控制

现状：

- `ReviewController`、`SystemConfigController`、`DashboardController`、`NotificationController` 均直接暴露 REST API。
- 未见 Spring Security、JWT、Session、SSO、RBAC 或网关注入用户身份的代码。
- `SystemConfigController` 可读写 GitHub Token、LLM API Key、MySQL/RabbitMQ 配置。
- `ReviewController` 可创建任务、重试任务、执行 GitHub 评论回写。

风险：

- 未授权用户可触发 PR 审查、写 GitHub 评论、读取系统配置摘要、修改审查规则。
- 企业内部系统若只依赖网络隔离，一旦代理配置、VPN 或网关规则异常，后端无第二道防线。

优化建议：

1. 接入企业统一认证，优先支持 OIDC/OAuth2 或网关注入可信用户头。
2. 建立角色模型：
   - `ADMIN`：系统配置、集成配置、规则管理。
   - `REVIEWER`：查看任务、预览和回写评论。
   - `DEVELOPER`：创建任务、查看自身仓库任务。
   - `OPS`：查看健康、配置测试、运行诊断。
3. 后端增加方法级权限控制：
   - 配置写接口必须 `ADMIN`。
   - GitHub 回写必须 `REVIEWER` 或更高。
   - 仪表盘和任务列表至少需要登录。
4. 所有配置变更记录真实操作者，替换当前系统设置中固定 `admin` 的审计写法。

验收标准：

- 未登录访问 `/api/v1/**` 返回 401。
- 权限不足访问配置写接口返回 403。
- 配置变更日志包含真实用户、来源 IP、变更类型、结果。
- 前端根据权限隐藏或禁用不可用操作。

### P0-02 生产加密密钥强制校验与密钥轮换方案

现状：

- `SecretCryptoService` 使用 AES-GCM 加密，技术选型正确。
- `repoguard.security.encryption-key` 未配置时默认 `repoguard-local-dev-encryption-key`。
- `decrypt` 对无 `enc:v1:` 前缀的值直接原样返回，兼容明文存量配置。

风险：

- 生产环境误用默认密钥时，所有 Token/API Key/服务密码加密强度退化。
- 明文兼容逻辑长期保留，可能让历史明文配置静默继续使用。
- 未定义密钥轮换、密钥版本、重新加密流程。

优化建议：

1. 在 `prod` profile 启动时强制校验：
   - `repoguard.security.encryption-key` 必填。
   - 禁止等于本地默认值。
   - 长度和复杂度满足企业密钥规范。
2. 扩展密文格式为 `enc:v2:{keyId}:{payload}`，支持密钥版本。
3. 增加配置重加密任务：
   - 读取旧密文。
   - 使用旧 key 解密。
   - 使用新 key 加密。
   - 写入前备份配置表。
4. 对无前缀明文值增加启动告警和管理页风险提示，要求保存后转为密文。

验收标准：

- 生产未配置密钥时应用启动失败。
- 默认密钥在生产 profile 下启动失败。
- 配置表敏感字段全部以 `enc:` 开头。
- 密钥轮换流程有演练记录和回滚说明。

### P0-03 拆分审查执行长事务

现状：

- `ReviewTaskExecutorImpl.execute` 标注 `@Transactional`。
- 同一事务内执行：
  - 任务状态更新为 `REVIEWING`。
  - 调用 GitHub 拉取 diff。
  - 调用 LLM。
  - 删除并插入 changed files。
  - 删除并插入 findings。
  - 更新任务为 `COMPLETED` 或 `FAILED`。

风险：

- GitHub/LLM 慢响应会拉长数据库事务，持有连接和潜在锁资源。
- 外部调用失败时，事务回滚可能影响已写入的执行轨迹。
- 高并发下连接池更容易被 Worker 长时间占用。

优化建议：

1. 将执行链路拆为短事务阶段：
   - `markReviewing(taskId)`：短事务。
   - `fetchDiff`：无事务外部调用。
   - `saveChangedFiles`：短事务。
   - `callReviewer`：无事务外部调用。
   - `saveReviewResult`：短事务。
   - `markFailed`：独立短事务，保证失败状态落库。
2. timeline 写入使用独立事务，确保失败轨迹不因主流程异常丢失。
3. 外部调用结果先形成内存领域对象，再进入数据库写入阶段。
4. 为任务状态更新增加乐观条件：
   - 只允许 `QUEUED -> REVIEWING`。
   - 只允许当前执行实例将 `REVIEWING -> COMPLETED/FAILED`。

验收标准：

- GitHub 或 LLM 超时不持有数据库事务。
- 外部调用失败后任务稳定进入 `FAILED`，timeline 保留失败原因。
- 并发重复消费同一消息时不会重复执行完整审查。

### P0-04 RabbitMQ 失败治理、重试退避与死信队列

现状：

- `RabbitMqConfig` 声明持久化 exchange、queue、binding。
- `application.yml` 使用 `acknowledge-mode: auto`、`prefetch: 1`、`concurrency: 1`。
- `ReviewTaskWorker` 固定 `@RabbitListener(..., concurrency = "1")`。
- 未见 DLQ、重试退避、消息 TTL、手动 ack、失败消息隔离。

风险：

- Worker 抛出未捕获异常时消息处理语义不清晰。
- 下游短时不可用时缺少退避策略，容易快速重试打爆外部服务。
- 毒丸消息缺少隔离，会影响后续任务消费。
- `review_policy_config.worker_concurrency` 已配置但未真正驱动 listener 并发。

优化建议：

1. 队列拓扑增加：
   - `repoguard.review.dlx`
   - `repoguard.review.dlq`
   - retry queue 或延迟重试机制。
2. 采用手动 ack 或明确 Spring AMQP retry 策略。
3. 增加错误分类：
   - 可重试：网络超时、GitHub 5xx、LLM 5xx、RabbitMQ 瞬断。
   - 不可重试：PR 不存在、Token 权限不足、请求参数错误。
4. `mq_retries` 与真实 MQ 重试次数对齐。
5. Worker 并发从配置读取，并增加运行时保护上限。

验收标准：

- 模拟 LLM 超时，消息按退避策略重试。
- 超过最大重试进入 DLQ，任务状态为 `FAILED` 且原因可读。
- 毒丸消息不阻塞后续正常任务。
- RabbitMQ 管理台可观察主队列、重试队列、死信队列数量。

## 6. P1 优化项

### P1-01 外部调用治理：GitHub 与 LLM 限流、熔断和错误分类

现状：

- GitHub 调用集中在 `GithubPullRequestClientImpl`。
- LLM 调用集中在 `LlmPullRequestReviewer` 和连接测试逻辑。
- LLM 已有超时配置和规则 fallback。
- GitHub/LLM 错误目前主要通过异常文本归类。

风险：

- GitHub 401/403/404/422/429/5xx 需要稳定分类，否则失败建议可能不准确。
- LLM 供应商慢响应时缺少熔断和并发保护。
- 评论回写可能触发 GitHub rate limit。

优化建议：

1. 引入 Resilience4j 或等价能力：
   - timeout
   - retry
   - circuit breaker
   - rate limiter
   - bulkhead
2. 为 GitHub API 建立统一错误映射：
   - `github_token_missing`
   - `github_token_invalid`
   - `github_permission_denied`
   - `github_target_not_found`
   - `github_rate_limited`
   - `github_validation_failed`
   - `github_server_error`
3. 对 LLM 调用记录：
   - 请求耗时。
   - 响应状态。
   - 解析成功/失败。
   - fallback 原因。
4. 对评论回写增加批量节流，避免短时间大量 POST。

验收标准：

- 429、403、404、422 均能稳定转为中文可读建议。
- LLM 连续失败后熔断生效，并进入规则 fallback 或明确失败状态。
- 指标可按 GitHub/LLM 错误类型聚合。

### P1-02 任务幂等与并发唯一性保护

现状：

- `triggerManualReview` 先查询同一 organization/repository/prNumber/commit 是否存在，再插入。
- 数据库未见 `(organization, repository, pr_number, commit_sha)` 唯一索引。
- MQ 重复消息时 `execute` 只跳过 `COMPLETED`，对 `REVIEWING`、`FAILED` 的并发保护不足。

风险：

- 并发创建同一 PR/commit 时可能产生重复任务。
- 重复消费时可能重复删除/写入 changed files 和 findings。
- 评论回写虽然有 finding 级唯一表，但并发发布仍需数据库唯一约束与事务保护配合。

优化建议：

1. 增加唯一索引：
   - `uk_review_task_pr_commit(organization, repository, pr_number, commit_sha)`
2. 插入任务时捕获唯一键冲突并返回 existing task。
3. 状态流转使用条件更新：
   - `update ... where id = ? and status = 'QUEUED'`
4. 任务执行增加 `execution_id` 或 `locked_at`，用于恢复卡住的 `REVIEWING` 任务。
5. 评论回写批次与 finding 幂等表在并发发布时使用唯一键冲突处理。

验收标准：

- 20 个并发请求创建同一 PR/commit，只产生一个任务。
- 重复 MQ 消息不会重复写 findings。
- 并发点击评论回写不会重复发布 GitHub 评论。

### P1-03 配置一致性与运行时诊断

现状：

- 上线实测报告显示 MySQL/RabbitMQ 配置页连接测试失败，但运行中的服务正常。
- `SystemConfigServiceImpl` 同时支持保存“配置页中的服务配置”和读取当前 Spring 环境属性。
- 运维视角容易混淆“运行时连接”与“配置表待测连接”。

风险：

- 管理员可能误以为当前 MySQL/RabbitMQ 不可用。
- 配置表与环境变量双来源时，缺少优先级和同步策略。

优化建议：

1. 配置页拆分为两个状态：
   - 当前运行时状态：来自 Spring DataSource/RabbitTemplate 实际连接。
   - 配置表状态：用于下一次保存/测试的目标配置。
2. UI 明确显示“运行中配置来源”：
   - 环境变量。
   - 数据库配置表。
   - 默认值。
3. 连接测试结果增加：
   - testedConfigSource。
   - runtimeHealthy。
   - savedConfigHealthy。
   - mismatch 字段。
4. 生产环境建议 MySQL/RabbitMQ 只由环境变量或配置中心管理，页面只读展示。

验收标准：

- 运维能一眼区分当前服务是否健康和保存配置是否可用。
- 配置表为空不导致运行时状态显示失败。
- 生产 profile 下可禁用页面修改基础设施连接配置。

### P1-04 可观测性指标与结构化日志

现状：

- Actuator 仅暴露 `health,info`。
- 业务状态主要存在数据库表中。
- 未见统一 traceId、结构化业务日志、Micrometer 自定义指标。

风险：

- 线上排障依赖查库和人工复现。
- 无法对 GitHub/LLM/MQ/DB 的错误率和耗时建立告警。

优化建议：

1. 暴露 Prometheus 指标或企业监控兼容端点。
2. 增加核心指标：
   - `repoguard_review_task_created_total`
   - `repoguard_review_task_completed_total`
   - `repoguard_review_task_failed_total{category}`
   - `repoguard_review_duration_seconds`
   - `repoguard_github_api_requests_total{operation,status}`
   - `repoguard_llm_requests_total{status}`
   - `repoguard_llm_fallback_total{reason}`
   - `repoguard_comment_publish_total{status}`
   - `repoguard_mq_queue_depth`
3. 日志增加字段：
   - `traceId`
   - `taskId`
   - `repository`
   - `prNumber`
   - `operation`
   - `durationMs`
   - `failureCategory`
4. 错误日志禁止输出 Token、API Key、完整 diff。

验收标准：

- 监控平台可看到任务成功率、失败率、耗时 P95。
- GitHub/LLM 错误可按类别告警。
- 任一任务可通过 taskId 从日志串联完整链路。

### P1-05 数据库索引、归档与慢查询治理

现状：

- `review_task` 已有 repository、status+created、risk+created、keyword、source、trigger_source 索引。
- changed files、findings、timeline 有 task 维度索引。
- `retention_days` 已配置，但未见归档/清理任务。
- 回写历史查询当前按任务全量返回，未分页。

风险：

- 长期运行后 review_task、review_finding、timeline、publication_batch_item 增长明显。
- 仪表盘聚合和任务列表查询可能出现慢查询。
- 无归档会增加备份和恢复成本。

优化建议：

1. 增加任务唯一索引和常用组合索引：
   - `uk_review_task_pr_commit`
   - `idx_review_task_repo_status_created(repository, status, created_at)`
   - `idx_review_task_repo_risk_created(repository, risk_level, created_at)`
2. 为 dashboard 聚合建立必要索引或物化统计表。
3. 增加数据归档任务：
   - 按 `retention_days` 清理普通任务。
   - 高风险任务、回写历史按更长周期保留。
   - 清理前导出审计归档。
4. 回写历史接口增加分页和状态筛选。

验收标准：

- 1 万任务下任务列表 P95 < 1s。
- 仪表盘 P95 < 2s。
- 归档任务可配置、可 dry-run、可审计。

### P1-06 异常响应脱敏与错误码稳定化

现状：

- `GlobalExceptionHandler` 对未知异常返回 `exception.getMessage()`。
- 前端 `request` 在 HTTP 非 2xx 时只提示 `HTTP status`，可能丢失后端统一错误体。

风险：

- 后端可能把内部异常、下游响应、路径或 SQL 信息暴露给前端。
- 前端对业务错误提示不稳定，排障效率低。

优化建议：

1. 未知异常对外统一返回“系统繁忙，请稍后重试”，详细信息只进日志。
2. 保留稳定错误码：
   - `BAD_REQUEST`
   - `TASK_NOT_FOUND`
   - `GITHUB_TOKEN_MISSING`
   - `GITHUB_PERMISSION_DENIED`
   - `GITHUB_RATE_LIMITED`
   - `LLM_TIMEOUT`
   - `MQ_UNAVAILABLE`
3. 前端在非 2xx 时尝试解析 `ApiResponse`，优先展示 `message/code`。
4. 错误响应增加 `traceId`，便于用户把问题反馈给运维。

验收标准：

- 构造 RuntimeException 时前端不展示堆栈或内部路径。
- 所有核心业务失败有稳定 code。
- 用户截图可包含 traceId，运维可定位日志。

## 9. 分模块代码审查结论

### 9.1 后端 Controller 层

优点：

- 接口路径清晰，统一使用 `/api/v1`。
- 分页参数已限制 `pageSize <= 100`。
- 写接口使用 `@Valid` 校验请求体。

问题：

- 缺少认证授权。
- 配置管理接口敏感度高，但未做角色隔离。
- 部分 PathVariable 只做长度或最小值校验，缺少枚举白名单。

建议：

- 引入认证授权后，按接口敏感度设置权限。
- 对 `status`、`riskLevel`、`source`、`triggerSource` 增加枚举校验。

### 9.2 后端 Service 层

优点：

- `ReviewServiceImpl` 对任务列表、详情、评论预览、回写、历史、重试形成闭环。
- `SystemConfigServiceImpl` 对敏感配置有脱敏和保留旧密钥占位值逻辑。
- 回写历史区分当前 finding 发布状态和批次审计轨迹，方向正确。

问题：

- `ReviewServiceImpl` 职责较重，超过 1000 行，聚合了查询、任务创建、GitHub 回写、历史、失败分类、DTO 转换。
- 配置服务同样较重，包含 GitHub、MySQL、RabbitMQ、LLM、规则、系统设置。
- 部分错误分类基于异常 message，稳定性不足。

建议：

- 拆分为：
  - `ReviewQueryService`
  - `ReviewCommandService`
  - `GithubCommentService`
  - `ReviewFailureClassifier`
  - `IntegrationConfigService`
  - `ConnectionTestService`
- 错误分类使用异常类型和 HTTP status，不依赖自由文本。

### 9.3 Worker 与消息层

优点：

- 队列消费链路简单直接。
- 任务状态和 timeline 可追踪。

问题：

- 外部调用在事务中执行。
- listener 并发写死为 1，未使用配置。
- 缺少 DLQ、退避、手动 ack。
- `ReviewTaskPublisher` 未启用 publisher confirm/return 处理。

建议：

- 按 P0-03、P0-04 改造。
- 发布消息失败时，任务创建事务需要明确处理策略：
  - 插入任务成功但消息失败时标记 `FAILED/MQ_UNAVAILABLE`。
  - 或采用 outbox 表，由后台可靠投递。

### 9.4 GitHub 集成

优点：

- 支持 open PR 列表、diff 文件、行评论、PR 评论、head SHA 解析。
- 行评论失败可降级为 PR 总评评论。
- 已设置 GitHub API version header。

问题：

- 缺少分页拉取全部 changed files，目前 `/pulls/{pullNumber}/files` 默认分页可能只返回第一页。
- open PR 列表固定 `per_page=50`，无分页参数。
- 错误分类仍偏文本化。
- mark checked 会在业务调用中更新配置状态，可能把临时失败写成配置失败。

建议：

- changed files 支持 GitHub 分页，直到无下一页或达到系统 maxDiffLines。
- open PR 列表支持分页和缓存。
- 运行时调用失败只记录运行健康事件，不直接覆盖配置页状态，或区分 `lastRuntimeError` 与 `lastConfigTestError`。

### 9.5 LLM 审查

优点：

- 支持 OpenAI Chat Completions 兼容接口。
- 有 timeout、max tokens、temperature、规则 fallback。
- Parser 支持较多非标准 JSON 场景。

问题：

- prompt 和 compact diff 限制硬编码在代码中。
- `max_diff_lines` 系统设置未明显接入 LLM prompt 截断。
- 缺少 LLM 成本、token、fallback 率指标。
- LLM 原始输出不保存，审查质量追踪困难；若保存则必须脱敏和限长。

建议：

- 将 diff 截断策略配置化。
- 按文件类型、文件大小、敏感路径做预过滤。
- 记录模型调用元数据，不记录完整敏感 diff。

### 9.6 数据库与 Migration

优点：

- Flyway 版本连续。
- 核心表、配置表、回写历史表结构完整。
- 多数查询维度已有基础索引。

问题：

- 缺少 PR/commit 任务唯一约束。
- 外键未设置级联策略，删除/归档需要额外脚本管理。
- V2 seed demo data 生产执行策略需要更明确。
- 回写历史明细表后续增长快，需要分页和归档。

建议：

- 新增 V10 migration，包含唯一索引、组合索引、必要归档字段。
- 生产环境明确禁用或隔离 demo seed。
- 增加归档策略和 DBA 审批流程。

### 9.7 前端

优点：

- API 封装集中。
- 页面覆盖完整。
- 已使用 TypeScript 类型。
- Vite 已配置基础 manualChunks。

问题：

- API 错误处理对非 2xx 过于粗糙。
- 类型与后端 DTO 手工同步，存在漂移风险。
- 系统设置页面包含调试预览文本，生产 UI 应确认是否保留。
- 详情页完整轮询可能造成不必要负载。

建议：

- 优先优化 `api/client.ts` 错误解析。
- 引入状态接口与轮询退避。
- 建立契约生成或契约测试。
- 生产构建前检查页面无调试信息。

  - `sourceEncryptionKey` / `sourceKeyId`：旧密钥信息。

  - `execute=false`：默认预检，只输出报告，不写数据库。

  - 旧 `enc:v2:{oldKeyId}:...` 密文。
  - 旧 `enc:v1:...` 密文。
  - 历史明文敏感值。
  - 已经使用目标 keyId 的密文会跳过。
  - 解密失败的字段会标记为 `FAILED`，不写回。
- `SecretCryptoService` 新增 `encryptedKeyId()` 和 `activeKeyId()`，供重加密报告和目标 key 判断使用。

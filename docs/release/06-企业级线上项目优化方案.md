# RepoGuard Agent 企业级线上项目优化方案

文档版本：v1.0  
编制日期：2026-06-10  
适用项目：RepoGuard Agent  
审查范围：`repoguard-backend`、`repoguard-frontend`、`docs/release`、Flyway migration、构建与运行配置  
审查角色：资深架构师 / 企业级线上交付评审

## 1. 结论摘要

RepoGuard Agent 已具备企业内部 PR 智能审查平台一阶段上线的核心闭环：任务创建、RabbitMQ 异步执行、GitHub diff 拉取、LLM/规则审查、审查结果展示、失败重试、评论预览与回写、回写历史追踪、配置管理和基础验收文档。

从企业级线上项目标准看，当前代码更接近“可进入预发和灰度”的状态，距离“稳定生产长期运行”还需要补齐以下关键能力：

| 优先级 | 结论 | 上线影响 |
| --- | --- | --- |
| P0 | 认证授权、生产密钥强制校验、长事务拆分、MQ 失败治理必须先处理或由网关/运维方案强约束 | 未处理不建议直接开放生产访问 |
| P1 | GitHub/LLM 调用治理、任务幂等并发保护、配置一致性、可观测指标、数据库索引与归档需要进入近期迭代 | 影响稳定性、排障效率和容量 |
| P2 | 前端错误可读性、状态轻量轮询、历史分页、构建产物优化、接口版本化需要持续优化 | 影响体验和运维效率 |
| P3 | 文档模板、代码规范、规则市场、审查质量反馈闭环可作为后续增强 | 不阻塞一阶段上线 |

建议上线策略：

1. 生产发布前完成 P0 项，或给出等效外部控制措施和验收记录。
2. P1 项进入首个生产稳定性迭代，建议 1-2 个 Sprint 内完成。
3. P2/P3 纳入产品体验和平台化路线图。

## 2. 当前方案定位

本方案作为 RepoGuard Agent 企业级上线和持续优化的总控文档，保留结论、优先级、路线图、准出清单、架构优化规则和进度索引。

详细实施记录已拆分到 [`06-progress/`](./06-progress/README.md)。历史审查依据、模块级审查底稿和已完成事项的展开过程不再放在主文档中，避免主方案继续膨胀。

当前系统已具备任务创建、RabbitMQ 异步执行、GitHub diff 拉取、LLM/规则审查、审查结果展示、失败重试、评论预览与回写、配置管理、认证授权、审计、通知和基础观测能力。后续重点转向生产稳定性、架构边界收敛、查询性能、状态语义、前端可维护性和审查质量闭环。

## 6. 最终建议

RepoGuard Agent 的功能闭环和工程骨架已经比较完整，当前最大的风险不在“功能是否能跑通”，而在“生产长期运行时是否能安全、可控、可恢复”。因此，后续优化应优先围绕安全边界、外部依赖治理、短事务、消息失败隔离、幂等并发、可观测性和数据生命周期展开。

推荐结论：

- 可以继续推进预发和灰度评审。
- 不建议在未完成 P0 项或未落实等效外部控制前直接开放生产访问。
- P1 项应在首次生产稳定性迭代中集中处理，避免上线后靠人工查库和临时脚本维持运行。

## 7. 架构优化专项沉淀

本节合并自原 `docs/architecture-optimization-handoff.md`，仅保留可长期维护的架构判断、执行规则和后续目标；旧交接文档中的新对话 Prompt、临时文件清单、当时工作区提醒等一次性内容不再保留。

### 7.1 架构总体判断

当前系统仍适合保持“增强型单体”形态：

- Spring Boot 单体后端、RabbitMQ 异步任务、MySQL/Flyway 主存储、Vue 管理台的组合仍匹配当前规模。
- 外部调用治理、缓存、审计、认证授权和基础观测能力已逐步补齐，主要风险不在技术选型。
- 后续优化重点应放在应用内职责边界、查询模型、状态语义、配置读取、前端页面和类型分域上。
- 暂不建议过早拆微服务；服务边界尚未稳定前，微服务会提前引入鉴权、链路追踪、部署编排、分布式事务和运维复杂度。
- 暂不建议用 Redis 替代 Caffeine；只有出现多实例部署、跨实例限流、分布式锁、幂等 key 共享等明确需求时再评估。

### 7.2 架构优化执行规则

本规则用于约束后续架构优化执行过程。除非项目负责人明确调整，否则每次优化均按以下规则执行。

- 所有架构优化工作统一在 `PRAgent-test` 分支进行，不直接在 `main` 分支改动。
- 主分支只作为同步来源和最终合并目标，不承载直接开发。
- 开始改动前先确认当前分支、远端同步状态和工作区状态，避免混入无关变更。
- 优化应小步实施，每次只优化一个清晰边界，避免一次性大重构。
- 优先保持 Controller、API 响应结构、前端调用方式和外部调用契约不变。
- 当前阶段优先拆 Service 巨类、Provider、Builder、Query Service，先拆职责，再谈拆服务。
- 后端 Java 代码必须符合阿里 Java 编程规范，重点关注命名、职责边界、异常处理、日志、事务、集合与空值处理。
- 涉及 Java 代码改动时，提交前必须运行相关单元测试；影响范围较大时运行后端全量测试。
- 涉及前端改动时，提交前必须运行前端类型检查或构建。
- 测试通过后才能提交、推送，并按流程合并到目标分支；测试未通过时不得进入提交、推送和合并环节。
- 如果依赖、网络或环境限制导致测试无法执行或结果不可信，不提交、不推送，先记录阻塞并等待处理。
- 提交和 stage 必须定向选择文件，不能把本地日志、临时脚本、密钥、token 或无关工作区改动混入。
- 生产环境密钥、token、连接信息不能写入文档或提交。
- 缓存不替代架构优化：慢查询、职责混乱、重复逻辑应从设计上解决，不能只靠缓存遮蔽。
- 领域边界优先：按配置、审查任务、GitHub 评论、Dashboard、通知、前端页面域收敛职责。
- 每完成一项架构优化，必须同步更新 `06-progress/` 中对应日期记录；记录至少包含优化日期、编号或名称、已完成内容、验证命令与结果、阶段结论以及下一步建议或遗留事项。
- 只有相关测试、类型检查或构建验证通过后，才能在优化文档中标记为“已完成”；尚未验证、验证失败或受环境限制的事项必须如实标记为“进行中”或“阻塞”，并记录原因。
- 优化进度文档必须与对应代码变更同步更新，避免文档进度与仓库实际状态不一致。

### 7.3 已推进的架构方向

- `ReviewServiceImpl` 已从早期巨类逐步收敛为门面服务，查询、命令、反馈、GitHub 评论发布等职责已外移。
- 审查任务状态机已建立，审查执行、重试、人工审核、评论发布等关键判断开始集中。
- Dashboard 已引入聚合 Mapper，主要统计从全量内存聚合转向 SQL 聚合。
- GitHub、ReviewPolicy、ReviewRule、SystemSettings、RabbitMQ 等配置 Provider 已逐步出现。
- 前端已开始围绕 Dashboard、ReviewDetail、NotificationOps、Integrations 等页面拆分组件、composable、类型和样式边界。

### 7.4 后续优先级

高优先级：

- 继续拆分 `SystemConfigServiceImpl`，重点保持集成配置、审查规则、系统设置、连接测试等边界清晰。
- 继续拆分 GitHub 评论链路，保持预览、发布、发布历史、失败分类、风险画像、PR 摘要等能力可独立测试。
- 补齐 `HumanReviewStatus`、`LlmStatus` 等枚举边界，减少字符串状态判断残留。

中优先级：

- 继续审查 `ReviewTaskQueryServiceImpl`、`ReviewTaskExecutorImpl`、通知投递链路等应用服务是否还有重复 DTO 组装、状态派生或落库边界可收敛。
- Dashboard 后续重点转向 SQL 可验证性：明确索引假设、时间窗口、`EXPLAIN` 记录和大数据量下的读模型演进。
- MessageQueue、Notification、GitHub 写回等运维能力继续保持查询、命令、补偿、响应组装边界分离。

前端后续目标：

- 继续降低大页面和全局样式耦合，页面层只保留路由参数、主布局和组合编排。
- 请求、轮询、状态归一化、派生文案、确认弹窗流程优先下沉到 composables 或领域组件。
- 类型按领域维护，避免重新回到单个 `types/index.ts` 中堆叠所有 DTO。

### 7.5 暂不投入方向

- 暂不拆微服务：当前复杂度主要来自应用内职责边界，不是部署单元过大。
- 暂不用 Redis 替换 Caffeine：除非多实例、跨实例限流、分布式锁、幂等窗口等需求明确出现。
- 暂不做一次性大重构：继续采用“门面不变、内部委托、小步迁移、测试护航”的方式。

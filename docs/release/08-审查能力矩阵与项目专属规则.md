# RepoGuard Agent 审查能力矩阵与项目专属规则

更新时间：2026-06-20
用途：沉淀 RepoGuard Agent 面试项目中“规则 + LLM + 评测集”的审查能力边界，避免只把项目讲成通用 LLM 调用。

## 1. 核心定位

RepoGuard 的审查能力不只依赖模型提示词，而是由三层共同组成：

- 规则审查：稳定命中确定性工程风险，低成本、可解释、可测试。
- LLM 审查：处理跨文件语义、复杂上下文和修复建议表达。
- 离线评测集：为规则、prompt、parser、chunk 和合并策略提供回归基线。

面试表达可以聚焦为：

> 我把 AI Code Review 做成了可治理的工程能力。规则层负责稳定兜底，LLM 负责语义判断，评测集负责防止 prompt 和规则迭代时质量退化。

## 2. 审查能力矩阵

| 维度 | 目标风险 | 默认等级 | 是否可能阻断 | 当前落点 |
| --- | --- | --- | --- | --- |
| 安全 | 硬编码密钥、敏感日志、配置明文、权限缺失 | HIGH | 是 | `RG-SECRET-001`、`RG-LOG-001`、`RG-AUTH-001` |
| 稳定性 | 宽异常、固定休眠、状态机绕过、未收敛 TODO | MEDIUM | 视场景 | `RG-JAVA-001`、`RG-JAVA-003`、`RG-STATE-001`、`RG-GEN-001` |
| 消息可靠性 | MQ 发布失败无补偿、消费缺幂等、重试状态不可见 | HIGH | 是 | `RG-MQ-001`、LLM 评测 case |
| 外部调用治理 | 无超时、无错误分类、无熔断限流、无指标 | MEDIUM | 视场景 | `RG-EXT-001`、LLM 评测 case |
| 数据库兼容性 | 破坏性 migration、缺索引、默认值不兼容 | HIGH | 是 | `RG-DB-002`、`RG-DB-003`、LLM 评测 case |
| GitHub 回写 | 评论重复发布、绕过 publication 记录、批次审计缺失 | HIGH | 是 | `RG-GH-001`、发布服务幂等边界 |
| 测试质量 | 核心分支、失败路径、契约变更缺测试 | MEDIUM | 视场景 | `RG-API-001`、评测集 |
| 架构维护性 | 巨类职责混杂、DTO/实体边界混乱、重复派生逻辑 | MEDIUM | 否 | 架构优化 A 系列边界抽取 |

## 3. 首批项目专属规则

| 规则 ID | 名称 | 触发点 | 价值 |
| --- | --- | --- | --- |
| `RG-AUTH-001` | 写接口权限门禁 | Controller 新增 POST/PUT/PATCH/DELETE 映射 | 防止配置写入、用户管理、评论回写等高危操作绕过权限 |
| `RG-SECRET-001` | 硬编码密钥检测 | password、secret、token、apiKey 等字面量 | 防止 GitHub Token、LLM API Key、Webhook secret 泄露 |
| `RG-LOG-001` | 敏感日志检测 | 日志输出 token、secret、password、webhook 等字段 | 防止生产日志成为密钥泄露面 |
| `RG-STATE-001` | 任务状态机绕过检测 | 直接写入 QUEUED、REVIEWING、FAILED 等状态字符串 | 防止绕过状态机、claim fencing 和补偿语义 |
| `RG-MQ-001` | MQ 发布补偿语义检测 | 新增 RabbitMQ 直接发布调用 | 防止发送失败不可见、不可补偿 |
| `RG-EXT-001` | 外部调用治理检测 | 新增裸 RestClient/WebClient/HttpClient 调用 | 推动超时、错误分类、限流熔断和指标统一治理 |
| `RG-DB-002` | 破坏性数据库迁移检测 | `DROP TABLE`、`DROP COLUMN`、`TRUNCATE TABLE` | 防止灰度发布和回滚期间出现不可逆数据结构破坏 |
| `RG-DB-003` | 新增非空字段兼容性检测 | `ADD COLUMN ... NOT NULL` 且缺少 `DEFAULT` | 防止历史数据升级失败和多版本应用兼容问题 |
| `RG-GH-001` | GitHub 评论回写幂等检测 | 新增 GitHub 评论直接发布调用 | 防止绕过 finding 级 publication 和 batch 审计导致重复刷评论 |
| `RG-API-001` | Controller API 测试缺口检测 | Controller mapping 变更但同 PR 无测试文件 | 防止接口契约、权限、状态码和关键响应字段缺少回归保障 |

## 4. 评测集口径

离线评测集位于 `repoguard-backend/src/test/resources/review-quality/evaluation-cases.json`，当前覆盖 22 个代表性 case：

- 宽异常、标准输出、固定休眠、TODO、干净 PR。
- 硬编码密钥、破坏性数据库迁移、MQ 消费幂等、外部调用超时。
- LLM 与规则混合合并。
- 写接口权限门禁、状态机绕过、MQ 发布补偿、裸外部调用、敏感日志。
- 破坏性数据库迁移、新增非空字段兼容性、GitHub 评论回写幂等。
- Controller/API 变更缺测试、同 PR 包含测试时不误报。

验收要求：

- 每个新增规则至少有单元测试或评测 case。
- 评测集不依赖真实 GitHub、LLM 或生产资源。
- 规则、parser、prompt、chunk、合并策略调整后优先运行评测测试。

## 5. Finding 可解释性字段

当前规则审查、LLM 解析、`review_finding` 落库和任务详情 API 已支持以下结构化字段；前端展示可作为后续体验增强继续推进。

| 字段 | 含义 | 面试价值 |
| --- | --- | --- |
| `confidence` | HIGH/MEDIUM/LOW 置信度 | 区分确定性规则命中和低置信建议 |
| `evidence` | 触发依据摘要 | 让 reviewer 知道为什么报 |
| `impact` | 可能造成的线上影响 | 帮助判断处理优先级 |
| `fixExample` | 修复示例或修复方向 | 提升结果可采纳性 |
| `isBlocking` | 是否建议阻断合并 | 为后续合并门禁预留结构 |
| `reviewDimension` | ACCESS_CONTROL、DATABASE_COMPATIBILITY_RULE 等审查维度 | 支撑质量统计和误报分析 |

评测约束：

- 高风险规则 finding 必须 `confidence=HIGH`。
- 高风险规则 finding 必须 `isBlocking=true`。
- 高风险规则 finding 必须包含非空 `evidence`、`impact`、`fixExample` 和 `reviewDimension`。
- LLM 输出缺少增强字段时，parser 必须给出兼容默认值，避免模型漏字段导致解析失败。
- `review_finding` 历史数据必须通过数据库默认值兼容，新增数据由审查链路写入完整字段。

## 6. 简历表达建议

可写：

> 设计并落地 PR 审查能力矩阵，沉淀安全、稳定性、消息可靠性、外部调用治理、数据库兼容性、GitHub 回写幂等和 API 契约测试等多维审查分类；结合项目架构实现专属规则库，覆盖权限门禁、敏感信息脱敏、状态机约束、MQ 补偿、外部调用治理、敏感日志、数据库兼容迁移、评论回写幂等和 Controller 测试缺口；将 finding 结构化为置信度、证据、影响、修复示例和是否阻断合并，并建立 22 条离线评测 case，用于回归验证规则、Prompt、Parser、Chunk 与 LLM/规则合并策略。

不建议写：

- “LLM 审查准确率达到 XX%”，当前没有真实标注集支撑。
- “完全替代人工 Code Review”，系统定位是辅助审查和风险前置。
- “只靠大模型发现问题”，项目亮点恰恰是规则、评测、反馈和工程治理闭环。

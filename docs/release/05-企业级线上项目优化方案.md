# RepoGuard Agent 企业级线上项目优化方案

文档版本：v1.1
编制日期：2026-06-10
最近更新：2026-06-21
适用项目：RepoGuard Agent
审查范围：`repoguard-backend`、`repoguard-frontend`、`docs/release`、Flyway migration、构建与运行配置
审查角色：资深架构师 / 企业级线上交付评审

## 1. 结论摘要

RepoGuard Agent 已具备企业内部 PR 智能审查平台一阶段上线的核心闭环：任务创建、RabbitMQ 异步执行、GitHub diff 拉取、LLM/规则审查、审查结果展示、失败重试、评论预览与回写、回写历史追踪、配置管理和基础验收文档。

从企业级线上项目标准看，当前代码更接近“可进入预发和灰度”的状态，距离“稳定生产长期运行”还需要补齐以下关键能力：

| 优先级 | 结论 | 上线影响 |
| --- | --- | --- |
| P0 | 认证授权、生产密钥强制校验、长事务拆分、MQ 失败治理必须先处理或由网关/运维方案强约束 | 未处理不建议直接开放生产访问 |
| P1 | GitHub/LLM 调用治理、任务幂等并发保护、配置一致性、可观测指标、数据库索引与归档需要进入近期迭代 | 影响稳定性、排障效率和容量 |
| P2 | 前端错误可读性、状态轻量轮询、历史分页、构建产物优化、接口版本化需要持续优化 | 影响体验和运维效率 |
| P3 | 文档模板、代码规范、规则市场、审查质量反馈闭环可作为后续增强 | 不阻塞一阶段上线 |

建议上线策略：

1. 生产发布前完成 P0 项，或给出等效外部控制措施和验收记录。
2. P1 项进入首个生产稳定性迭代，建议 1-2 个 Sprint 内完成。
3. P2/P3 纳入产品体验和平台化路线图。

## 2. 当前方案定位

本方案作为 RepoGuard Agent 企业级上线和持续优化的总控文档，保留结论、优先级、路线图、准出清单、架构优化规则和进度索引。

详细实施记录已拆分到 [`05-progress/`](./05-progress/README.md)。历史审查依据、模块级审查底稿和已完成事项的展开过程不再放在主文档中，避免主方案继续膨胀。

当前系统已具备任务创建、RabbitMQ 异步执行、GitHub diff 拉取、LLM/规则审查、审查结果展示、失败重试、评论预览与回写、配置管理、认证授权、审计、通知和基础观测能力。后续重点转向生产稳定性、架构边界收敛、查询性能、状态语义、前端可维护性和审查质量闭环。

## 6. 最终建议

RepoGuard Agent 的功能闭环和工程骨架已经比较完整，当前最大的风险不在“功能是否能跑通”，而在“生产长期运行时是否能安全、可控、可恢复”。因此，后续优化应优先围绕安全边界、外部依赖治理、短事务、消息失败隔离、幂等并发、可观测性和数据生命周期展开。

推荐结论：

- 可以继续推进预发和灰度评审。
- 不建议在未完成 P0 项或未落实等效外部控制前直接开放生产访问。
- P1 项应在首次生产稳定性迭代中集中处理，避免上线后靠人工查库和临时脚本维持运行。

## 7. 架构优化专项沉淀

本节合并自原 `docs/architecture-optimization-handoff.md`，仅保留可长期维护的架构判断、执行规则和后续目标；旧交接文档中的新对话 Prompt、临时文件清单、当时工作区提醒等一次性内容不再保留。

### 7.1 架构总体判断

当前系统仍适合保持“增强型单体”形态：

- Spring Boot 单体后端、RabbitMQ 异步任务、MySQL/Flyway 主存储、Vue 管理台的组合仍匹配当前规模。
- 外部调用治理、缓存、审计、认证授权和基础观测能力已逐步补齐，主要风险不在技术选型。
- 后续优化重点应放在应用内职责边界、查询模型、状态语义、配置读取、前端页面和类型分域上。
- 暂不建议过早拆微服务；服务边界尚未稳定前，微服务会提前引入鉴权、链路追踪、部署编排、分布式事务和运维复杂度。
- 暂不建议用 Redis 替代 Caffeine；只有出现多实例部署、跨实例限流、分布式锁、幂等 key 共享等明确需求时再评估。

### 7.2 架构优化执行规则

本规则用于约束后续架构优化执行过程。除非项目负责人明确调整，否则每次优化均按以下规则执行。

- 所有架构优化工作统一在 `PRAgent-test` 分支进行，不直接在 `main` 分支改动。
- 主分支只作为同步来源和最终合并目标，不承载直接开发。
- 开始改动前先确认当前分支、远端同步状态和工作区状态，避免混入无关变更。
- 优化应小步实施，每次只优化一个清晰边界，避免一次性大重构。
- 优先保持 Controller、API 响应结构、前端调用方式和外部调用契约不变。
- 当前阶段优先拆 Service 巨类、Provider、Builder、Query Service，先拆职责，再谈拆服务。
- 后端 Java 代码必须符合阿里 Java 编程规范，重点关注命名、职责边界、异常处理、日志、事务、集合与空值处理。
- 涉及 Java 代码改动时，提交前必须运行相关单元测试；影响范围较大时运行后端全量测试。
- 涉及前端改动时，提交前必须运行前端类型检查或构建。
- 测试通过后才能提交、推送，并按流程合并到目标分支；测试未通过时不得进入提交、推送和合并环节。
- 如果依赖、网络或环境限制导致测试无法执行或结果不可信，不提交、不推送，先记录阻塞并等待处理。
- 提交和 stage 必须定向选择文件，不能把本地日志、临时脚本、密钥、token 或无关工作区改动混入。
- 生产环境密钥、token、连接信息不能写入文档或提交。
- 缓存不替代架构优化：慢查询、职责混乱、重复逻辑应从设计上解决，不能只靠缓存遮蔽。
- 领域边界优先：按配置、审查任务、GitHub 评论、Dashboard、通知、前端页面域收敛职责。
- 每完成一项架构优化，必须同步更新 `05-progress/` 中对应日期记录；记录至少包含优化日期、编号或名称、已完成内容、验证命令与结果、阶段结论以及下一步建议或遗留事项。
- 只有相关测试、类型检查或构建验证通过后，才能在优化文档中标记为“已完成”；尚未验证、验证失败或受环境限制的事项必须如实标记为“进行中”或“阻塞”，并记录原因。
- 优化进度文档必须与对应代码变更同步更新，避免文档进度与仓库实际状态不一致。

### 7.3 已推进的架构方向

- `ReviewServiceImpl` 已从早期巨类逐步收敛为门面服务，查询、命令、反馈、GitHub 评论发布等职责已外移。
- 审查任务状态机已建立，审查执行、重试、人工审核、评论发布等关键判断开始集中。
- Dashboard 已引入聚合 Mapper，主要统计从全量内存聚合转向 SQL 聚合。
- GitHub、ReviewPolicy、ReviewRule、SystemSettings、RabbitMQ 等配置 Provider 已逐步出现。
- 前端已开始围绕 Dashboard、ReviewDetail、NotificationOps、Integrations 等页面拆分组件、composable、类型和样式边界。

### 7.4 后续优先级

高优先级：

- 继续拆分 `SystemConfigServiceImpl`，重点保持集成配置、审查规则、系统设置、连接测试等边界清晰。
- 继续拆分 GitHub 评论链路，保持预览、发布、发布历史、失败分类、风险画像、PR 摘要等能力可独立测试。
- 补齐 `HumanReviewStatus`、`LlmStatus` 等枚举边界，减少字符串状态判断残留。

中优先级：

- 继续审查 `ReviewTaskQueryServiceImpl`、`ReviewTaskExecutorImpl`、通知投递链路等应用服务是否还有重复 DTO 组装、状态派生或落库边界可收敛。
- Dashboard 后续重点转向 SQL 可验证性：明确索引假设、时间窗口、`EXPLAIN` 记录和大数据量下的读模型演进。
- MessageQueue、Notification、GitHub 写回等运维能力继续保持查询、命令、补偿、响应组装边界分离。

前端后续目标：

- 继续降低大页面和全局样式耦合，页面层只保留路由参数、主布局和组合编排。
- 请求、轮询、状态归一化、派生文案、确认弹窗流程优先下沉到 composables 或领域组件。
- 类型按领域维护，避免重新回到单个 `types/index.ts` 中堆叠所有 DTO。

### 7.5 暂不投入方向

- 暂不拆微服务：当前复杂度主要来自应用内职责边界，不是部署单元过大。
- 暂不用 Redis 替换 Caffeine：除非多实例、跨实例限流、分布式锁、幂等窗口等需求明确出现。
- 暂不做一次性大重构：继续采用“门面不变、内部委托、小步迁移、测试护航”的方式。

### 7.6 代码级架构审查与下一轮优化清单

本节合并 2026-06-21 代码级架构审查结果，用于指导下一轮优化排序。当前系统已经具备可演示、可灰度验证的核心闭环，下一轮不建议优先继续堆功能，也不建议过早拆微服务。主要风险来自应用内职责边界继续膨胀，以及少数核心类承担过多线上关键逻辑。

下一轮优化应聚焦：

1. 外部依赖边界清晰化。
2. 任务创建与执行链路职责拆分。
3. 状态枚举和状态机继续收敛。
4. 数据库读模型和压测结论固化。
5. 前端大页面继续瘦身。

#### OPT-ARCH-001：修复 GitHub 客户端分页与职责过载

优先级：P0/P1

当前 `GithubPullRequestClientImpl` 同时负责 PR 列表、diff 文件拉取、评论发布、行评论失败降级、GitHub 健康状态更新和指标记录。该类已经成为 GitHub 集成的复杂度中心。

更关键的是，PR 列表目前只取 `per_page=50`，diff 文件接口没有明确分页处理。真实大 PR 可能存在 changed files 超过单页限制的情况，导致审查漏文件。

建议拆分：

- `GithubPullRequestReader`：读取 PR 列表和 PR metadata。
- `GithubChangedFileReader`：分页读取 changed files。
- `GithubCommentWriter`：负责行评论和 PR 总评评论发布。
- `GithubPaginator`：统一处理 GitHub 分页。
- `GithubIntegrationHealthReporter`：集中记录连接健康和最近错误。

验收标准：

- 覆盖 30、50、100+ changed files 的分页测试。
- PR 列表和 changed files 不因单页限制漏数据。
- 评论发布降级逻辑仍保持原有行为。

#### OPT-ARCH-002：收敛任务创建服务，移除静态线程池和静态内存聚合

优先级：P1

当前 `ReviewTaskCommandServiceImpl` 仍承担任务创建、幂等、afterCommit 发布、重试、人工复核、时间线、来源解析等多种职责，类体量偏大。

同时该类包含静态 `ConcurrentMap`、静态 `ExecutorService` 和静态 `ScheduledExecutorService`。这类静态运行时资源不利于 Spring 生命周期管理，也不利于测试隔离、优雅关闭和后续监控。

建议拆分：

- `ManualReviewCreationService`：负责新建任务和复用已有任务。
- `ManualReviewIdempotencyCoordinator`：负责同 PR + commit 的短窗口并发聚合。
- `ReviewTaskAfterCommitPublisher`：负责事务提交后的消息发布。
- `ReviewTaskRetryService`：负责失败任务重试。
- `HumanReviewCommandService`：负责人工复核决策。

验收标准：

- 任务创建 20/50/100 并发幂等结果保持不变。
- 静态线程池替换为 Spring Bean，并具备关闭能力。
- 后端相关单测通过。

#### OPT-ARCH-003：继续拆分 Worker 执行编排与事务落库

优先级：P1

当前 `ReviewTaskExecutorImpl` 仍同时处理消息执行、任务 claim、GitHub diff 拉取、审查调用、结果落库、失败处理、通知和缓存驱逐。虽然已经通过 `READ_COMMITTED` 和有限重试降低并发写入死锁风险，但核心编排类仍偏重。

建议拆分：

- `ReviewExecutionWorkflow`：只保留执行流程编排。
- `ReviewTaskClaimService`：负责领取、释放和 claim fencing。
- `ReviewExecutionResultWriter`：负责 changed files、findings、timeline 和任务终态写入。
- `ReviewExecutionFailureHandler`：负责失败分类、失败状态和失败时间线。
- `ReviewExecutionNotifier`：负责完成、失败、人工复核通知。

验收标准：

- Worker 并发 1/2/4 的既有测试继续通过。
- 事务重试逻辑集中在结果写入层。
- `ReviewTaskExecutorImpl` 不再直接操作多个子表 mapper。

#### OPT-ARCH-004：拆分 MQ 健康查询和重入队命令

优先级：P1

当前 `MessageQueueHealthServiceImpl` 同时承担 MQ 健康查询、运行时连接探测、异常任务聚合、手动重入队、审计和时间线写入。查询和命令职责混在一起，后续容易造成运维接口和写操作互相影响。

建议拆分：

- `MessageQueueHealthQueryService`：负责健康响应和异常任务列表。
- `ReviewTaskRequeueService`：负责人工重入队命令。
- `RabbitRuntimeHealthProbe`：负责 RabbitMQ runtime 连接探测。
- `MessageQueueAuditRecorder`：负责操作审计。

同时应统一 `DLQ` 等状态定义，避免数据库状态、DTO 状态和 `ReviewTaskStatus` 枚举不一致。

验收标准：

- `/api/v1/message-queue/health` 只读路径不依赖写命令逻辑。
- 手动重入队行为和审计记录保持不变。
- `DLQ`、`PUBLISH_FAILED` 等状态有统一枚举或明确边界说明。

#### OPT-ARCH-005：统一任务来源、发布状态和回写状态枚举

优先级：P1

当前任务主状态已经有 `ReviewTaskStatus` 和 `ReviewTaskStateMachine`，这是好的基础。但任务来源、触发来源、GitHub 回写状态、发布批次状态等仍存在字符串分散问题，例如 `MANUAL_INPUT`、`GITHUB_PR_PICKER`、`EXISTING_REUSED`、`already_published`、`downgraded_to_pr_comment`。

建议补齐：

- `ReviewTaskSource`
- `ReviewTaskTriggerSource`
- `GithubCommentPublicationStatus`
- `GithubCommentTargetType`
- `NotificationEventStatus` 与 DTO 映射边界

验收标准：

- 后端业务判断不直接散落裸字符串。
- DTO 输出仍保持前端需要的小写格式。
- 相关 mapper、assembler、service 单测覆盖未知值和空值。

#### OPT-ARCH-006：连接测试策略化

优先级：P2

当前 `ConnectionTestServiceImpl` 直接知道 GitHub、LLM、MySQL、RabbitMQ 的连接测试细节，并直接构造部分 probe。新增一个 provider 会继续扩大该类。

建议引入统一策略接口：

```text
ConnectionProbe {
    provider()
    probeSavedConfig()
    probeSubmittedConfig()
    markChecked()
}
```

GitHub、LLM、MySQL、RabbitMQ 各自实现 probe。应用服务只负责路由、权限和响应组装。

验收标准：

- 新增 provider 不需要修改一个大方法。
- 保存配置测试和临时提交配置测试语义清晰。
- 连接失败时仍能返回可读错误。

#### OPT-ARCH-007：规则审查器插件化

优先级：P2

当前 `RuleBasedPullRequestReviewer` 支持根据配置判断规则是否启用，但规则检测逻辑仍集中在一个类中，包括敏感字段、TODO/FIXME、Controller 测试缺口、数据库 migration 风险、外部调用治理等。

建议引入规则插件接口：

```text
ReviewRule {
    id()
    supports(context)
    evaluate(context)
}
```

规则引擎负责加载已启用规则、过滤适用文件、汇总 finding。单条规则独立测试。

验收标准：

- 现有规则行为保持不变。
- 每条规则可以单独单测。
- 项目专属规则可以新增实现类，不再修改一个巨型 reviewer。

#### OPT-ARCH-008：前端继续瘦身大页面

优先级：P2

前端已经抽出部分 composable 和组件，但页面层仍偏重。当前较大的页面包括：

- `LoginPage.vue`
- `ReviewDetailPage.vue`
- `NotificationOpsPage.vue`

其中任务详情页仍保留大量 computed、确认弹窗和展示派生逻辑。页面层应只保留路由参数、主加载和组合编排。

建议拆分：

- 登录页拆为 `LoginForm`、`RegisterForm`、`AuthHeroPanel`。
- 任务详情页将确认弹窗流程下沉 composable。
- 状态文案、tag class、失败说明等下沉 display mapper。
- 通知运维页继续拆 settings、events、deliveries 三个区域。

验收标准：

- 页面路由行为不变。
- 前端类型检查和构建通过。
- 大页面行数持续下降，业务逻辑进入 composable 或领域组件。

#### 下一轮建议执行顺序

1. 先做 `OPT-ARCH-001`，修复 GitHub 分页和客户端职责边界。这是最接近真实业务正确性的风险。
2. 再做 `OPT-ARCH-002`，收敛任务创建链路，移除静态运行时资源。
3. 然后做 `OPT-ARCH-003`，继续拆分 Worker 执行和结果写入边界。
4. 接着做 `OPT-ARCH-004` 和 `OPT-ARCH-005`，统一 MQ 运维边界和状态模型。
5. 后续做 `OPT-ARCH-006`、`OPT-ARCH-007`、`OPT-ARCH-008`，提升可扩展性和前端可维护性。

#### 下一轮准出标准

完成下一轮架构优化时，至少满足：

1. 后端相关单测通过；涉及大范围改动时运行后端全量测试。
2. 前端改动必须通过类型检查和构建。
3. GitHub 分页、大 PR diff、任务创建并发幂等、Worker 并发写入至少各保留一组回归测试。
4. 代码改动同步更新本文档或对应进度文档。
5. 不混入本地日志、真实 token、真实密钥或无关压测产物。

### 7.7 当前阶段后续优化建议

截至 2026-06-22，`OPT-ARCH-001` 至 `OPT-ARCH-011-A` 已覆盖 GitHub 分页与职责边界、任务创建链路、Worker 执行边界、MQ 运维边界、状态枚举、连接测试策略化、规则插件化、前端大页面瘦身、查询链路、通知投递链路和 Dashboard SQL 验证计划等方向。后续不建议继续在已收口模块上做低收益拆分，应优先转向更接近生产准出、可验证性和契约稳定性的工作。

当前仍值得继续投入的方向：

1. `OPT-ARCH-011-B Dashboard SQL 索引匹配复核`
   - 对照 `DashboardMapper` 的过滤列、聚合列、排序列与 `DashboardSqlVerificationPlan` 中的索引假设。
   - 重点判断是否存在“SQL 使用方式”和“索引设计”不匹配。
   - 如需优化，优先补充 migration 索引或调整验证计划，不先改变 Dashboard 聚合语义和接口响应。

2. Dashboard 大数据量验证材料
   - 明确每个 Dashboard 聚合 SQL 的时间窗口、索引假设和建议 `EXPLAIN` 观察项。
   - 记录应关注的 `key`、`type`、`rows`、`Extra` 等指标。
   - 优先形成可复用验证说明，支撑预发和压测排障，而不是继续拆 Java 小类。

3. OpenAPI / 契约测试
   - 当前 Controller/API 响应结构依赖单测和人工约定保护，后续应补充更明确的接口契约防线。
   - 优先覆盖审查任务列表/详情/状态、GitHub 评论预览/发布、通知运维和 Dashboard overview 等核心接口。
   - 目标是防止后续架构优化误伤前端调用和外部集成契约。

4. 生产准出检查自动化
   - 将后端关键测试集合、前端类型检查和构建、`git diff --check`、migration 检查、密钥/token 泄漏检查等沉淀为可重复执行的准出检查。
   - 该方向比继续拆已经收口的小类更接近企业级上线质量保障。

当前不建议继续投入的方向：

- 暂不继续拆 `ReviewTaskQueryServiceImpl`、`ReviewTaskDetailDataLoader`、通知投递链路和已收口的前端大页面。
- 暂不为了降低行数继续抽 mapper、assembler、component 或 composable。
- 暂不扩张规则插件化细枝末节；若后续推进，应另起 patch 级 / PR 级规则插件接口专项。
- 暂不直接修改 Dashboard 聚合 SQL 语义；必须先证明索引、窗口或执行计划存在明确问题。

建议后续执行顺序：

1. `OPT-ARCH-011-B Dashboard SQL 索引匹配复核`。
2. Dashboard `EXPLAIN` / SQL 验证说明。
3. API 契约测试。
4. 生产准出检查自动化。
